## 3. Real defect found AND fixed (fail-then-pass verified) — **F156**

### F156 🟠 — accountant "add journal on behalf of client" never stamped `entity_id` (F150-class miss)

`POST /api/accountants/clients/:userId/journal` (`accountant-routes.js:640`) inserted into `journals`
**without an `entity_id`**. This is the one constrained-table insert F150 missed when it stamped
`entity_id` across the main app's business routes.

Two consequences, one latent and one live:

- **Cross-entity leak (latent, the F150 class):** a journal posted by an accountant was stored
  account-wide (`entity_id = NULL`). The null-inclusive read filter surfaces such a row under **every
  one** of that client's entities — a wrong ledger on every set of books, identical in shape to the
  leak F150 fixed everywhere else.
- **Hard break (live, post-constraint):** since 2026-08-12 `chk_journals_entity_nn` rejects the NULL
  outright, so the route now returns **HTTP 500** — the accountant journal feature is broken in
  production for any client.

**Evidence (fail-then-pass, `verify-f90-accountant-audit.js`):**

| | HEAD (before) | After fix |
|---|---|---|
| `POST …/journal` | **500** — `chk_journals_entity_nn`, failing row `(1, 1, null, …)` | **201** |
| audit-trail `journals/CREATE` row | absent (write never landed) | present, attributed to the accountant |
| harness total | **2 failed / 9 passed** | **11 / 0** |

**Root fix (one file, `accountant-routes.js`).** Resolve the client's active entity exactly as the
main app's entity-scope middleware does (`server.js:751` — active first, then lowest id), stamp it on
the insert, and return a clean 400 if the client genuinely has no entity (instead of a 500):

```js
const _entRow = await pool.query(
  `SELECT id FROM entities WHERE user_id = $1 ORDER BY (CASE WHEN (data->>'is_active')::int = 1 THEN 0 ELSE 1 END), id ASC LIMIT 1`,
  [parseInt(userId)]
);
const _clientEntityId = _entRow.rows[0]?.id ?? null;
if (_clientEntityId == null) return res.status(400).json({ error: 'Client has no entity to post against.' });
const { row } = await db.insert('journals', { user_id: parseInt(userId), entity_id: _clientEntityId, /* … */ });
```

**Class enumeration (Rule 13) — this is the ONLY remaining instance.** Every `db.insert` into a
constrained table was audited across both `server.js` and `accountant-routes.js`:

- `server.js` — all 17 constrained tables stamp `entity_id` (invoices, expenses, customers,
  inventory, items, quotes, vendors, bills, recurring_bills, recurring_invoices, sales_receipts,
  payments_received, payments_made, credit_notes, vendor_credits, journals, chart_of_accounts),
  including the recurring generators at `server.js:3572/3596` which inherit `r.entity_id`.
- `accountant-routes.js` — only two `db.insert` calls: `journals` (this fix) and `lock_settings`
  (**not** a constrained table — correctly no `entity_id`).

No regression: after the fix, the full F150 family is still green — `verify-f150-entity-stamp-no-leak`
9/0, `verify-f150c-write-side-isolation` 33/0, `verify-f150d-entity-constraint` 19/0,
`verify-entity-leakage-sweep` "ALL SCOPED — no leaks" 18/0, `verify-f148-credit-entity-leak` 5/0 —
and the accountant-routes consumers `verify-f138-accountant-taxlines` 6/0 and
`verify-f140-accountant-fyear` 5/0.

## 5. Second defect found AND fixed — **F157** 🟢 LOW

### F157 — a business write by a user with no active entity returned a generic 500, not a clean 400

`POST /api/auth/register` creates **no default entity** (verified: the register route inserts only a
`users` row). Business routes stamp `entity_id = req.entityId`; with no entity that is `NULL`, and
`chk_*_entity_nn` then made the insert throw a generic **500**. In normal use this never fires — the
SPA onboarding flow POSTs `/api/entities` before the user reaches any create surface
(`finflow-api-wiring-postgres.js:115`, `app-main.js:535`) — which is exactly why the route-driven
harnesses in §4 shape (b) were test-debt, not product defects. But a direct-API caller, or any race
that reaches a create before onboarding completes, got an opaque 500 rather than a clean 400.

**Root fix (single shared mechanism, Rule 9).** Guarded at the one write path every business create
routes through rather than patching 17 routes: `db.insert` (`database.js`) knows the 17
entity-required tables and, on a null `entity_id` for one of them, throws a typed client-safe error
(`status:400, expose:true, code:'NO_ACTIVE_ENTITY'`); the global error handler (`server.js:5609`)
exposes that one message and leaves everything else a generic 500. All 17 create routes use `wrap()`
and their idempotency catches re-throw non-`23505`, so the typed error reaches the handler. This
matches the pattern the holdings route already used in isolation (`server.js:1620`), now applied to
the whole class, and a new create route cannot ship without it.

**Verified (fail-then-pass):** new harness `verify-f157-no-entity-400.js` — a no-entity user POSTs
invoices, expenses, bills, customers, vendors, journals, chart-of-accounts; each returns **400**
naming the entity (never 500): **15/0**. Pre-fix the same requests 500'd (reproduced in `verify-f79`
/ `verify-f133`). No happy-path regression: step-gates **150/0**; the C1 dedup family across all
constrained tables all green.
