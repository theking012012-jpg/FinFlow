## 1. What D2 requires (the decision)

A future-dated invoice/bill/expense contributes **0 to every figure — including Year — and to AR —
until its own date arrives** (`AUDIT_MASTER.md` D2). Three consequences were logged: (a) the app
allowed future dates with no bound and no scheduled state; (b) "future relative to whose clock?" —
a hard dependency on server-side period resolution (F88/F89) so the cutoff isn't the viewer's
browser clock; (c) a Part A check (A9) + a future-dated seed row are needed.

## 2. Evidence that D2 is already built

### Server — `computeBooks` (server.js)
- **Period resolution is server-side (F89 landed).** `_today = FinFlowDates.resolvedToday(new Date())`
  is the **server** clock as a UTC calendar **string** (server.js:4758). The client sends *intent*
  (`period` = `'month'|'quarter'|'year'` + `monthIdx`), and the server resolves the window via
  `FinFlowDates.resolvePeriod(...)` (4762-4766). The old client-instant window is accepted only for
  the golden master.
- **The D2 upper bound is in `inPeriod`, applied to every period (server.js:4774-4778):**
  ```js
  const inPeriod = v => {
    const ymd = FinFlowDates._toYmd(v);
    if (ymd == null || ymd > _today) return false;   // D2
    return ymd >= winStart && ymd < winEnd;
  };
  ```
  Every recognition leg routes through it — revenue (4869), sales receipts (4870), expenses (4889),
  bills (4915), payroll (4970), credit/vendor contras (4883/4984), COGS (5011).
- **AR/outstanding carries the same D2 bound (server.js:5037):** `_y != null && _y <= _today`
  — "future-dated invoices are scheduled, not receivable."
- All comparisons are **string-to-string** off the server clock (F87 / Rule 10), so the cutoff is
  **viewer-independent**.

### Client — `app-main.js` (mirrors the server)
- `computeRevenue` / period filter: "string compare + D2 (never recognise a row dated after today) —
  identical to the server" (1989-1992).
- AR: "D2 — a future-dated invoice is SCHEDULED, not yet receivable (mirrors the server AR leg)"
  (2066-2073, `if (_dy==null||_dy>_arToday) return;`).
- Scheduled-state helper (F94): `isScheduled(dateStr)` = `y > resolvedToday(...)` (649-653), used to
  badge the row so a post-dated document is **labelled, not vanished**.

## 4. Genuinely still open — the *broader* F87/F88 class (NOT D2 itself)

These were surveyed under F88 and are separate from the D2 cutoff, which is done:

- **F88 2b — display currency is per-user, applied at read time.** Stored nowhere server-side
  (`window._displayCurrency`); two viewers with different display currencies see figures that
  reconcile only through a moving rate. This is the last live viewer-dependence in the F88 class.
  *Owner decision needed:* make display currency an entity property, or accept labelled per-viewer
  conversion. (Appendix B / FX pass territory.)
- **F88 2e — the entity has no timezone.** Calendar dates are fixed by string compare (done), but
  genuine timestamps (`run_date`, `created_at`) assigned to a month still need *someone's* zone; with
  no entity timezone the code falls back to UTC (phase 1). Fine for calendar-dated money; the
  "phase 2" note in the code anticipates an entity timezone if instant-based bucketing is ever wanted.
- **F89 residual — a wrong client *day* still picks the wrong "current" period client-side.** Phase-1
  UTC made figures timezone-independent (step4 green), and `/api/reports` re-resolves server-side, so
  the *server* figures are clock-trustworthy. But the client's own `_fyContext` still derives "which
  period is current" from `new Date()` (app-main.js:1977). Low severity (a wrong system clock is the
  user's own machine), tracked under F89's "done when."

## 5. Known limitation to record (not a bug)

**Cash-flow applies no per-row D2** (app-main.js:2018-2023): a future-dated cash event inside the
*current* month would be included by the cash engine. The seed has no future cash event, so it is
untested, and it matches what the Cash Flow report shows (same rows/source). If a future cash event
is ever seeded, this is the assertion to add. Logged here so it isn't rediscovered as a surprise.
