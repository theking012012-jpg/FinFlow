# F88 — Entity-timezone & locale resolution (scope)

**Written:** 2026-08-21 · **Status:** scoped, not built · **Blocks:** the Scheduled Documents page (F94)
and correct day-edge behaviour for every genuine-timestamp surface.

This is the design/scope pass. No code shipped. Build it in the order below, each step verified against the
harness before the next.

---

## 0. The problem in one line
"Today" and every auto-dated event currently resolve to **UTC**, but a set of books belongs to an **entity**,
and each entity lives in its own timezone / country / currency. A user running a US company and a Canadian
company must get a US "today" for the US books and a Canadian "today" for the Canadian books — today they
both get UTC.

## 1. What already exists (don't rebuild)
- **`resolvedToday(serverNow, tzOrOffset)`** (`public/finflow-dates.js`) already has the seam:
  it accepts `tzOrOffset` and documents a `PHASE 2 HOOK`, but currently does `void tzOrOffset; return _utcYmd(d)`.
  Phase 1 (UTC, viewer-independent) shipped on purpose. **F88 = implement phase 2 here.**
- **`nextRunDate(currentDate, frequency)`** (`server.js`) is already timezone-free integer Y/M/D math (F159).
  The recurrence arithmetic is correct — do **not** touch it. Only the *boundary comparison* is wrong.
- **Per-entity currency already works** — `entities.currency`, `_activeEntityCurrency()`, per-entity P&L
  conversion. Timezone/country should follow the same per-entity pattern currency set.
- **Entity scoping is everywhere** — `entity_id` on every table, active-entity toggle, `req.entityId`.

## 2. What's missing (the actual work)
1. **Entity has no `timezone` and no `country`.** `POST /api/entities` writes `{name, currency, color, …}`
   only. Add **`timezone`** (IANA, e.g. `America/Toronto`) and **`country`** (ISO-2, for holidays) to:
   - the entity create/edit routes + validation (reject a non-IANA zone),
   - the entity create/edit **UI** (a timezone picker; default from the browser but always explicit),
   - a **backfill** for existing entities (default to the owner's browser zone once, owner-confirmable).
2. **`resolvedToday` phase 2** — resolve the server instant into the *entity's* calendar date:
   `resolvedToday(serverNow, entityTz)` → the Y-M-D in that zone. Pure, deterministic, still
   viewer-independent (books have a zone, viewers don't). Unit-test the day-edge cases (e.g. 23:30 in
   `America/Port_of_Spain` is still "yesterday" in UTC).
3. **Scheduler becomes per-entity** — `runRecurringScheduler` currently does
   `const today = new Date().toISOString().slice(0,10)` (UTC) and one SQL sweep across all rows.
   Replace with: resolve each row's entity `today` from that entity's `timezone`, and only materialise when
   `next_run <= entityToday`. Practical shape: widen the candidate query to a ±1-day window, then filter in
   JS per entity zone (avoids a tz library in SQL). The materialised doc's `run_date` must be stamped in the
   entity's zone, not raw UTC `NOW()`.
4. **`_isScheduled` (client)** must pass the **active entity's** timezone into `resolvedToday`, so the blue
   "Scheduled" badge flips on the entity's local boundary, not the viewer's or UTC.
5. **Holiday / business-day shift (new, layered on top)** — with `entity.country` in place, a run landing on a
   weekend or a public holiday in that country can shift to the next business day. The holiday source is
   locale-driven (per entity country), never a hardcoded region. This is additive and can ship after 1–4.

## 3. Cautions carried from prior findings
- **Rule 6 / F34 invariant:** do NOT add a `created_at` fallback to receipts to synthesise a date — it breaks
  the recognition==filter invariant. Prefer **F85** (events carry their intended period explicitly) over any
  timestamp-inference fallback.
- **Recognition basis unchanged:** F88 changes only *when the day boundary falls*, not the accrual rules
  (F32) or the period resolver (F33/F25). The step-gate figures must be **byte-for-byte identical** after
  F88 for any entity whose zone is UTC — that's the safest regression assertion.
- **`nextRunDate` is timezone-free on purpose (F159).** Don't "fix" it to be tz-aware; the boundary, not the
  arithmetic, is where zone belongs.

## 4. Build order (each step green before the next)
1. Add `entity.timezone` + `entity.country` (schema-free JSONB, routes, UI, backfill). Harness: entity CRUD
   round-trips the new fields; a bad zone is rejected.
2. Implement `resolvedToday` phase 2 + unit tests for day-edge cases across several zones.
3. Repoint the scheduler to per-entity `today`; stamp `run_date` in entity zone. Harness: two entities in
   different zones, one clock instant that is "tomorrow" for one and "today" for the other — only the right
   one materialises. Add the reproducing negative control (Rule 14).
4. Pass entity tz into `_isScheduled`; jsdom check that the badge flips on the entity boundary.
5. Full `run-verification-sweep` — must stay **140/140**, and every UTC-zone figure unchanged.
6. (Additive) holiday/business-day shift, driven by `entity.country`.

## 5. How the Scheduled Documents page (F94) sits on top
Once 1–4 land, the F94 page reads the **active entity's** `timezone`, `currency`, and `country` and needs no
tz logic of its own: the calendar "today", the forecast horizon, the "posts today" boundary, and the holiday
shading all come from the entity. That's why F94 is the design step and F88 is its prerequisite — the mock is
already wired against exactly these entity fields.

## 6. Test surfaces to touch/extend
`verify-recurring-scheduler.js`, `verify-recurring-nextrun-tz.js` (already exercises tz-sensitive next-run),
plus new: an entity-timezone CRUD check, a `resolvedToday` phase-2 unit harness, and a two-entity
different-zone scheduler boundary check. Keep the golden step-gates as the "nothing moved for UTC" guard.
