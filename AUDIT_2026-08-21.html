02

Findings, ranked by what to do first

Severity is about risk to the live books and to your ability to ship safely — not code taste. Nothing here is an open money bug. The one High is a working-tree integrity hazard that could ship stale code if committed as-is.

HighH1

The on-disk finflow-bundle.js is badly out of sync with its sources

Your own build check flags it, and the drift is not cosmetic — 11,632 lines differ between the committed-on-disk bundle and what node bundle.js regenerates from the 10 wiring sources. Because index.html ships this concatenated bundle (not the individual wiring files), the app running from this working tree executes stale client code, and committing the tree as-is would push it to production. This is the exact OneDrive-revert hazard your 08-13 note recorded — still unresolved.

npm run bundle:check
[bundle:check] DRIFT — public/finflow-bundle.js is out of sync with its 10 wiring sources.
[bundle:check] A wiring source was edited without regenerating the bundle. Run: node bundle.js
bundle:check exit=0   // ← also a bug: DRIFT exits 0, so CI can't catch it (F83 family)
Fix: run node bundle.js before any commit (the F13 hook does this, but the working tree is currently drifted); and make bundle:check exit non-zero on drift so a stale bundle can't slip through.
MediumM1

Every connector's stored credential key is derived from SESSION_SECRET

The AES-256-GCM key that protects all bank / payroll / processor tokens (Plaid, Finch, Stripe Connect, WiPay, dLocal, Mercado Pago, Wise) is a plain SHA-256 of your session-signing secret. Two consequences: rotating SESSION_SECRET — the standard response to a leak — would silently make every stored connector credential undecryptable with no re-encryption path; and a single secret compromise yields both session forgery and all financial-connector plaintext.

server.js:4467
function _plaidKey(){ return crypto.createHash('sha256')
    .update('plaid-token:' + (process.env.SESSION_SECRET || '')).digest(); }
Fix: introduce a dedicated CONNECTOR_ENC_KEY, independent of the session secret, with a documented rotation/re-encrypt story.
MediumM2

The verification suite is not cold-run clean — 4 client harnesses flake

Not a product bug (see §01), but it matters against your own bar: "Done = every check green," and a green sweep is what lets a real regression surface loudly instead of at 3am. Today a cold sweep shows 4 reds that a re-run clears, so the suite can both cry wolf and, worse, mask a genuine failure behind assumed flakiness (the F83 hazard your runner already fights).

Fix: in the jsdom client harnesses, await settle() for boot data (not just for the function to be defined) before the first driven action; stabilise the recently-changed jsdomBoot.js. Small, mechanical, high-value.

Low — hardening & correctness polish

Real, but none is exploitable today or blocks launch. Grouped for a single hardening pass.

LowL1

No session regeneration on login

server.js:687

Login/register/admin-login promote the existing session in place with no req.session.regenerate() — the standard session-fixation hardening. Largely mitigated by saveUninitialized:false + httpOnly + SameSite=lax, so severity is low.

LowL2

Password-reset tokens stored in plaintext

server.js:726/730

Invite tokens are SHA-256-hashed at rest (server.js:3182); reset tokens are not. A DB read exposure would hand out directly-usable, unexpired reset tokens. Hash them the same way. (Entropy is otherwise strong; enumeration is correctly avoided.)

LowL3

CSP allows 'unsafe-inline' scripts

server.js:61/72

Helmet's CSP is disabled and the manual header keeps script-src 'unsafe-inline', removing CSP's XSS protection on pages that render financial data. frame-ancestors, object-src, base-uri are correctly locked — the inline-script allowance is the gap.

LowL4

/api/ai reads books by user id, not account scope

server.js:3410/3434

Not a cross-tenant leak (a user reads their own data), but for an invited member it summarises the member's own empty books instead of the account they're scoped to — inconsistent with every other route, which use scopeId(req).

LowL5

Dead-code shadowing remains structurally live

109 overrides · ~23 shadow · 7 wrappers

Your #1 historical failure class is still the architecture: 109 window.X= overrides in the wiring files, ~23 of them shadowing a now-dead app-main.js copy, 7 true wrappers (_orig*). The runtime winners are correct today — but every future edit still has to answer "which copy actually runs?" first. This is debt, not a live bug; F92 tracks the structural cleanup.

LowL6

Typeface split across surfaces

Jost vs DM Sans

The main app pairs Cormorant Garamond with Jost; the accountant, admin, and landing pages pair it with DM Sans. Two body faces across one product reads as unfinished to a sharp eye. Pick one. (Both load from the Google Fonts CDN — a runtime external dependency worth noting.)

LowL7

Status vocabularies aren't enforced at the schema

F79

The database carries very few CHECK constraints; invoice/payroll status vocabularies are enforced only by app code and the harness gate. It's the exact shape of the status:'final' failure your CLAUDE.md opens with — a real INSERT would not reject a bad status. Defense-in-depth gap, already tracked.

LowL8

CRON_SECRET compare can throw on a wrong-length header

accountant-routes.js:913

timingSafeEqual needs equal-length buffers; a malformed header throws a RangeError → generic 500 instead of a clean 401. It still fails closed (no access). The admin-password path handles this correctly with fixed-length buffers — mirror that.

03

Security posture — the part that surprised me

For a solo-built SaaS this backend is defensively engineered to a genuinely high standard. I traced every injection sink, every mutating route, and the multi-tenant boundary. The findings above (M1, L1–L4, L8) are the whole list — everything below is what's already right, verified by reading the actual lines.

Verified sound

read at file:line, not assumed

  • ✓No SQL injection. Every interpolation resolves to a code constant, an allow-listed table name, or a bound placeholder. No user value reaches a query string.
  • ✓Every mutating /api route is behind auth. The only unauthenticated writes are intentional (auth, token-gated invite accept, signature-verified webhooks, CRON-secret payout).
  • ✓Tenant isolation holds. Reads go through allByUser(scopeId), writes gate on ownedBy(...). No query returns rows without a tenant filter — no entity leakage found.
  • ✓RBAC is fail-closed on the server-resolved role, executed green 30/0.
  • ✓Webhooks verify signatures (Stripe SDK, WiPay MD5 with length-guarded timing-safe compare) before any state change.
  • ✓Credentials AEAD-encrypted at rest and never returned to a client; the error handler leaks nothing on the primary path.

Hardening & transport

helmet · cors · sessions · limits

  • ✓Session cookie: httpOnly, secure in prod, SameSite=lax, 7-day expiry, PG-backed; SESSION_SECRET mandatory at boot.
  • ✓CORS fails safe (locked to ALLOWED_ORIGIN), trust proxy:1, body caps (500 KB default / 10 MB uploads).
  • ✓Rate limiting split read 600/min vs write 300/min, plus a tight 10-per-15-min auth limiter.
  • ✓Passwords bcrypt cost-12; admin + CRON secrets use timingSafeEqual.
  • △Gaps are the CSP inline-script allowance (L3) and session-fixation hardening (L1) — both Low.
